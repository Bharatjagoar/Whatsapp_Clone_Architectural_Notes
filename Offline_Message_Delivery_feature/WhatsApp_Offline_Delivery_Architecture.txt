================================================================================
ChatMeSerivice — Offline Message Delivery: Architecture Decision Log
================================================================================
Covers: Lane 1 (enqueue request) → Lane 2 (fetch offline messages) → Lane 3
(confirm delivery status). Three files involved:
  - processOfflineMessages.js  (main service — sends request, waits for reply)
  - MarkDelivery.js            (message service — queries Mongo, replies)
  - updateDeliveryStatus.js    (message service — marks delivered in Mongo)

I'm logging each decision as: PURPOSE → PROBLEM → SOLUTION → HISTORY (where
HISTORY only appears if I changed my mind after first implementing something,
because a new test case or a flaw I hadn't considered showed up later).

================================================================================
DECISION 1 — Reply Queue Design: Anonymous Exclusive Queue Per Request
================================================================================

PURPOSE
When a user reconnects, the main service needs to ask the message service for
that user's offline messages, and needs a private channel to receive the
reply on.

PROBLEM
I originally named the reply queue after the userid:
    const replyQueue = `offline.reply.${userid}`;
This queue was shared across every request from the same user. If a user
reconnected twice in quick succession — logs in, immediately refreshes the
page, a scenario I actually expect to happen in practice — two separate
requests would both attach a consumer to the SAME queue. RabbitMQ doesn't
deliver a message to every consumer on a queue, it picks one (competing-
consumers behavior). So request A's reply could get handed to request B's
consumer by mistake. I had a correlationId check in place to catch the
mismatch, but that didn't actually save me: the wrong consumer would just
ack-and-discard the message, request A's consumer would never receive
anything and would hang forever, and the user's offline messages would be
silently lost for that connection attempt.

SOLUTION
I switched to a RabbitMQ-generated anonymous queue, unique per individual
request instead of per user:
    const { queue: replyQueue } = await channel.assertQueue("", {
      exclusive: true,
      autoDelete: true,
    });
Passing an empty string as the queue name tells RabbitMQ to generate a
guaranteed-unique name for that specific call. Two concurrent requests from
the same user now get two physically different queues, so there's no
competing-consumer scenario at all — misdelivery becomes structurally
impossible instead of something I'm just detecting and working around after
the fact.

HISTORY
I initially considered naming the queue after the correlationId instead
(`offline.reply.${correlationId}`) — that would've worked equally well,
since correlationId is also unique per request (from uuidv4()). I went with
the anonymous RabbitMQ-generated name instead because it delegates the
uniqueness guarantee to the broker rather than me hand-building the string,
and it matches the idiomatic RPC pattern RabbitMQ itself recommends (close
to the built-in amq.rabbitmq.reply-to mechanism). No functional difference
between the two — just a naming/idiom preference, not a bug fix.

DECISION 2 — Removal of correlationId
================================================================================

PURPOSE
I'd added correlationId as a second layer of verification: once a reply
landed in a queue, check its correlationId matched what I expected, to guard
against the reply belonging to a different request.

PROBLEM
That was necessary defense back when queues were shared per-user (Decision
1's original design) — the correlationId check was the only thing standing
between "wrong message accepted" and "wrong message rejected." But it never
actually prevented the wrong message from being CONSUMED in the first place
— it only stopped it from being misused once consumed. The message would
still get silently discarded by the wrong consumer, and the rightful
consumer would still hang forever. So correlationId was solving the wrong
half of the problem the whole time.

Once I implemented Decision 1 (anonymous exclusive queue per request),
correlationId became vestigial — with one queue per request, nothing else
can ever land in that queue, so the "is this really my reply" check can
never meaningfully fail. I was keeping a field in every payload and a check
in every consumer for zero remaining benefit.

SOLUTION
I removed correlationId entirely — stopped generating it (dropped the
`uuidv4()` import), stopped including it in payloads, stopped checking it in
the consumer callback. Simplified the message shape across all three files.

HISTORY
This was a reversal I made mid-build. I'd first told myself to keep both —
anonymous queue for routing, correlationId for identity verification —
treating it as harmless "belt and suspenders" defense. It took actually
tracing through what the check could still catch, post-Decision-1, to
realize it could never trigger anymore. Once I saw that, I called it what it
was: dead code, not defense in depth, and pulled it out. The trigger for
reversing wasn't a new bug — it was re-examining what the "defense" was
actually still defending against and realizing the answer was nothing.

DECISION 3 — Error Signaling in Reply Payloads
================================================================================

PURPOSE
I needed the message service to be able to tell the main service "here are
your offline messages" versus "something went wrong on our end, we couldn't
fetch your messages" — two very different situations that the main service,
and ultimately the user, needs to be able to tell apart.

PROBLEM
Originally my replies were bare arrays:
    channel.sendToQueue(replyTo, Buffer.from(JSON.stringify(messages)));
That meant an empty array could mean one of two things with no way to tell
them apart: (a) the user genuinely has zero offline messages — the normal,
happy path — or (b) I tried and failed to fetch messages (say, after
exhausting retries during a Mongo outage) and gave up, sending an empty
array as a last resort. From the main service's side, and ultimately the
user's, both looked identical — the user would just appear to have no
offline messages, no indication anything had gone wrong. The messages would
stay `status: "sent"` in Mongo and only surface again on the user's NEXT
reconnect, but they'd have no way of knowing that's what happened.

SOLUTION
I changed every reply payload to a consistent object shape instead of a bare
array:
    { error: boolean, messages: array }
`error: false` on genuine success, including the legitimate zero-messages
case. `error: true` when I've given up after failure. The main service now
checks the `error` flag explicitly and logs a distinct message ("failed to
fetch offline messages... will retry on next reconnect") instead of
silently treating a failure the same as an empty inbox.

HISTORY
I wasn't satisfied leaving failure indistinguishable from empty and decided
against it outright once I actually thought through what it meant for the
user. Fixing it meant touching every single sendToQueue call across both
MarkDelivery.js and processOfflineMessages.js to keep the payload shape
consistent everywhere — success paths, the invalid-userid discard path, the
permanent-failure path, the retry-exhausted path. I deliberately went with
ONE consistent shape everywhere rather than bare-array-on-success and
object-on-failure, because a mixed shape felt like exactly the kind of thing
that causes silent bugs later — which is the whole category of problem I was
trying to get out of in this feature.

DECISION 4 — Bounded Retry on Transient Mongo Failures (MarkDelivery.js)
================================================================================

PURPOSE
MarkDelivery queries MongoDB for a user's offline messages. That query can
fail if MongoDB is briefly unreachable — a real scenario I want to handle,
not a hypothetical one: a user can log in and immediately refresh the page,
and if Mongo hiccups in that exact window, the request would previously be
lost outright.

PROBLEM
My original catch block treated every error identically:
    channel.nack(message, false, false);
`requeue: false` discards the message permanently on ANY error, including a
one-second Mongo connection blip that would very likely have succeeded on a
retry a moment later. I wasn't distinguishing a transient failure (worth
retrying) from a permanent one (retrying is pointless — e.g. malformed
input).

SOLUTION
I now categorize errors by `error.name`:
  - `MongooseServerSelectionError` or `MongoNetworkError` → transient. I
    retry the same query in a loop, waiting 1 second between attempts, for
    up to 10 seconds total, before finally giving up.
  - Anything else → permanent. I reply immediately with
    `{error: true, messages: []}` and discard without retry.

I deliberately did NOT use RabbitMQ's native nack-with-requeue-and-retry-
count mechanism, which would've needed custom message headers, since nack()
can't modify a message before requeuing — I'd have had to ack-then-republish
just to increment a counter. Instead, the retry happens entirely in-process,
a plain while-loop against a timestamp deadline, with the original message
staying unacked the whole time. I made this call because I'd already ruled
out needing a Dead Letter Exchange (see Decision 6's history) — DLX felt
like unnecessary machinery for a problem a simple time-bounded retry already
solves.

HISTORY
I went back and forth on this before settling:
  1. First I checked whether JS even has Java-style typed exceptions to
     distinguish error categories — it does, via `error.name` on the
     specific error classes Mongoose/the MongoDB driver throw.
  2. I considered a DLX plus message-header retry-count approach — the
     "correct production answer" on paper, but it meant restructuring nack
     into ack-and-republish. I dropped it once I was honest with myself
     about the actual requirement: for both a brief blip and a longer
     outage, the correct behavior is the same — retry for a bounded window,
     then give up cleanly. That doesn't need DLX at all; DLX solves a
     different problem (permanently routing failed messages for later
     manual inspection), not "retry for N seconds then bail."
  3. I settled on the in-process while-loop retry as the simplest thing
     that actually matches what I need, holding the message unacked for the
     retry window instead of touching RabbitMQ's redelivery mechanics at
     all.

Known accepted gap, not fixed, deliberately left alone: no backoff. If Mongo
is down for the full 10 seconds, I'm retrying every 1 second flat, no
increasing delay — that could add load during a real outage. Acceptable at
my current scale, revisit later if it isn't.

DECISION 5 — Timeout Protection on the Waiting Consumer (processOfflineMessages.js)
================================================================================

PURPOSE
After sending a request to MarkDelivery, processOfflineMessages sits in a
`channel.consume()` callback waiting for a reply. That wait needs a bound —
what happens if no reply ever arrives?

PROBLEM
Without a timeout, if MarkDelivery crashed entirely, or hung for some reason
outside the retry logic in Decision 4, or a reply landed on a queue that no
longer had an active consumer, this would wait indefinitely. Every
occurrence leaks one queue and one hung consumer for the life of the
process — no upper bound, and the user's connection handling would never
actually resolve.

SOLUTION
I added a 15-second timeout — deliberately longer than MarkDelivery's
10-second retry window from Decision 4, so MarkDelivery gets a fair shot at
finishing its own retries before I give up waiting on it. If the timeout
fires before a reply arrives, it cancels the consumer and logs it. A
`timedOut` flag guards a race where a genuine reply arrives right as the
timeout is about to fire — the consumer callback checks that flag first and
ignores late replies once timed out, and on the success path I call
`clearTimeout()` immediately so the timer doesn't fire spuriously after I've
already handled the message.

HISTORY
This is a mistake worth being honest about: I designed and wrote this fix
correctly early on, but didn't actually apply it to my real file for several
sessions — a real gap between "I've written this code" and "this code is in
the file that runs." I only caught it when I went back to paste my current
file for an unrelated check and realized point 5 had never actually made it
in, despite me having said "done" earlier. Re-applied it, re-confirmed it
properly the second time. No design change here — this was a tracking gap
on my part, not a re-thought decision.

DECISION 6 — Removal of Dead Letter Queue (DLQ); Validation Moved Upstream
================================================================================

PURPOSE
updateDeliveryStatus.js marks messages as "delivered" in MongoDB once
they're confirmed received by the client. That update can fail for two
different kinds of reasons, and I had to decide what to do with a failure
that retrying will never fix — like a malformed MongoDB ObjectId showing up
in the batch.

PROBLEM (as I originally solved it)
I introduced a DLQ (`updateDeliveryStatus-dlq`): on a permanently malformed
ID, or any non-connection error, I'd forward the failing message to this
separate queue instead of silently discarding it, meaning to preserve it for
later audit or debugging.

Sitting with it longer, I realized this DLQ solved nothing. Tracing through
where a malformed ID could actually come from: `deliveredIds` inside
processOfflineMessages is built entirely from `msgs._id` — MongoDB's own
ObjectIds, from documents I'd already successfully queried and already
successfully delivered to the client. These values never pass through user
input or any external API anywhere in this flow. If a malformed ID ever
reached updateDeliveryStatus, that would mean a BUG somewhere upstream in my
own code — not a data-quality problem from an untrusted source. Given that,
there's nothing useful I can actually DO with a message sitting in a DLQ —
I can't "fix" a bad ObjectId by looking at it later; the fix has to happen
at the point the bad ID got generated, not downstream of it.

SOLUTION
1. I removed the DLQ entirely from updateDeliveryStatus.js — no more
   `updateDeliveryStatus-dlq` queue assertion, no more invalidIds-filter-
   and-forward block, no more mongoose import in that file (validation
   moved elsewhere, so it wasn't needed here anymore).
2. I added validation UPSTREAM instead, in processOfflineMessages.js, right
   before deliveredIds gets sent to updateDeliveryStatus:
     const validIds = deliveredIds.filter((id) =>
       mongoose.Types.ObjectId.isValid(id),
     );
   If any IDs fail this check, I log it explicitly as `"BUG: ..."` — not
   framed as a normal/expected path, because per the reasoning above this
   should structurally never happen given where these IDs come from. Only
   validIds get forwarded downstream.

Known accepted gap: if this upstream validation ever gets bypassed or has
its own bug, and a bad ID reaches updateDeliveryStatus anyway, it'll now
throw a Mongoose CastError inside the try block there. CastError isn't
`MongooseServerSelectionError` or `MongoNetworkError`, so it'll get
classified as a permanent (non-connection) failure and silently nack-
discarded with no DLQ and no trace, since I removed that safety net. I
thought this through deliberately rather than missing it — I'm trusting the
upstream validation to make this path unreachable in practice.

HISTORY
This is the decision I went back and forth on the most:
  1. I built the DLQ first as "the safer option," choosing it directly over
     just blindly discarding malformed IDs.
  2. Later, I stopped and asked myself: why did I even introduce a DLQ in
     the first place? I had to retrace my own reasoning, because I'd
     conflated it with an EARLIER, separate decision about whether Mongo
     connection outages needed a full DLX (dead letter exchange) — I'd
     already concluded NO on that one, a simple time-bounded retry was
     enough for connection issues (see Decision 4). The DLQ for malformed
     IDs was a distinct, later decision solving a different problem
     (poison messages, not outages), and I'd blurred the two together in my
     own head.
  3. Once I untangled that, it became clear connection-issue failures never
     actually reach the DLQ at all — they retry-and-requeue right inside
     updateDeliveryStatus. Only the malformed-ID case ever lands there.
     That made me ask what audit/debugging value a DLQ full of malformed
     IDs would actually give me.
  4. The answer: none, because these IDs come from my own database query,
     not external input — so a DLQ entry already represents an internal
     bug, and the real fix is to stop bad IDs from being generated or
     forwarded in the first place, not to store them for later.
  5. That led directly to removing the DLQ and adding upstream validation-
     as-tripwire in processOfflineMessages.js instead — the final
     architecture documented above.

This is a genuine example of changing direction because I looked at the
problem from a new angle, not because the first version was wrong given
what I knew at the time. The DLQ was a reasonable, defensive choice when I
built it — re-examining the actual data flow later is what showed me it
added complexity without adding real protection, and that the fix belonged
one layer upstream instead.

DECISION 7 — Sender Delivery Notification (Best-Effort, Fire-and-Forget)
================================================================================
New file: notifySenderDelivered.js (main service — receives delivery
confirmations, emits to the sender's socket if they're online)

PURPOSE
When a message was sent while the recipient was offline, and the recipient
later comes online and receives it (Lanes 1-3 completing), the ORIGINAL
SENDER has no way to find out in real time — their UI keeps showing "sent"
(single tick) even though the message has genuinely been delivered (should
be double tick). This decision closes that gap.

I narrowed the scope on this one after re-checking my own code: this
notification is ONLY needed for the delayed-delivery path (recipient
offline at send time). The synchronous online-send path, in my existing
`getthesocketID-forMessage` socket handler, already sets
`message.status = "delivered"` immediately via `emitWithAck` if the
recipient is online at send time — the sender already learns that
synchronously, in the same callback. I'd initially assumed that path had the
same gap and had to go re-read my own handler to confirm it didn't.

PROBLEM
updateDeliveryStatus.js (Decision 6's final form) updates MongoDB and stops.
It has no way to reach a live socket connection, because `io` (the
Socket.IO server instance) only exists in the MAIN service process —
updateDeliveryStatus.js runs in the separate MESSAGE service process, which
has no access to `io` at all.

On top of that, `updateMany` alone can't give me what I need to notify
anyone — it only returns a match/modify count summary, never the actual
updated documents. I briefly assumed I could get sender IDs straight out of
`updateMany`, and had to correct myself: it doesn't return document fields
like `senderID` at all. A separate query is unavoidable to get sender
information, no matter which order I run things in.

SOLUTION
Cross-process design, following the same RabbitMQ RPC pattern I already
built for Lanes 1-3, but INTENTIONALLY SIMPLER — fire-and-forget, no reply
queue needed, since the message service doesn't need confirmation that a
sender was successfully notified:

1. In updateDeliveryStatus.js, AFTER `updateMany` succeeds:
   - `messagedb.find({_id: {$in: ids}}, {senderID: 1})` — a second,
     necessary query to get sender IDs for the messages I just updated.
   - Group message IDs by sender (`bySender` object), so a batch of
     multiple delivered messages from different senders produces ONE
     notification per sender, not one per message.
   - For each sender, `channel.sendToQueue("notifySenderDelivered",
     {senderId, messageIds})` — fire-and-forget, no publisher confirms (see
     below for why).

2. New file, notifySenderDelivered.js, runs in the MAIN service where `io`
   actually exists. It consumes `notifySenderDelivered`, looks up the
   sender's live socket via the same Redis pattern I already use elsewhere
   (`redis.hGet(\`socket:${senderId}\`, "socket")`), and if a socket ID
   comes back, emits `messagesDelivered` to it. If the sender's offline at
   that moment, I drop the notification silently — no fallback, no queued
   retry-on-reconnect. Deliberate: MongoDB already has the correct
   "delivered" status by this point, so a dropped live notification just
   delays the sender seeing the double-tick until their next reload or
   reconnect. No data loss, no incorrect state — just a missed real-time
   UX update.

3. Ordering — I compared two options for step 1:
     Option A: updateMany FIRST, then find senderIDs.
     Option B: find senderIDs FIRST, then updateMany.
   I initially assumed Option B saved a round-trip and was wrong — both
   options cost the exact same two queries, just in a different order. The
   real deciding factor turned out to be correctness under partial failure:
   Option A guarantees I never fetch or act on sender data for an update
   that didn't actually persist. Option B risks holding sender data in hand
   while the subsequent updateMany could still fail — which opens a path to
   falsely telling a sender their message was delivered when the DB update
   never actually went through. I picked Option A for that reason, not for
   efficiency.

4. No publisher confirms on the `notifySenderDelivered` send. I thought
   about adding them and decided against it: the underlying "delivered"
   status is ALREADY safely persisted in MongoDB by the time this fire-and-
   forget send happens, so the notification itself is best-effort UX
   polish, not a correctness-critical guarantee. The narrow failure window
   this would protect against — RabbitMQ specifically unreachable in the
   same instant MongoDB was confirmed reachable — felt too rare and too
   low-stakes (worst case: a live UI update arrives late instead of not at
   all) to justify the added complexity of confirm-mode channels and
   failure handling for this one step.

5. Where the new one-time consumer gets started: NOT inside the per-socket
   connection handler (socket.js) — that file runs on EVERY single client
   connection, and registering a new `channel.consume(...)` there would
   create a growing pile of duplicate, competing consumers on the same
   queue, one per connection ever made. I put it in the main service's
   index.js instead, inside the `server.listen(...)` startup callback,
   alongside the existing one-time `Rabbit_MQ_connection()` call — the
   right category is "long-lived listener, starts once at process boot"
   (same category MarkDelivery/updateDeliveryStatus fall into on the
   message-service side), not "per-event action" (the right category for
   the sendToQueue calls already living in socket.js).

I pass `io` into notifySenderDelivered(io) as an explicit function argument
at that startup call site, rather than having notifySenderDelivered.js
require index.js back to grab `io` from its exports (index.js does
`module.exports = io`, which technically could be required elsewhere). I
considered the circular-import route specifically to keep index.js shorter,
and dropped it once I actually compared the code volume — passing `io` as
an argument versus importing it circularly comes out to basically one word
of difference, not a meaningful reduction, while the circular version
reintroduces real require-order fragility for nothing in return.

HISTORY
A few points I got wrong or conflated along the way, worth keeping on
record because they're genuine reasoning corrections, not just
implementation notes:
  1. I initially lumped "what's left on this feature" together with an
     unrelated open item (prefetch on MarkDelivery) — caught myself and
     separated "what's left in the offline-delivery FEATURE" from "what's
     generally still open" as two different lists. Prefetch doesn't belong
     under this feature.
  2. I assumed `updateMany` could hand me the sender IDs directly (since it
     "gets you the exact message docs" — it doesn't). Correcting that
     directly shaped why a second `find` query is unavoidable no matter
     which ordering I chose.
  3. I assumed Option B (find-then-update) saved a round-trip over Option A
     — wrong, both cost the same two queries. The real distinguishing
     factor is correctness under partial failure, not efficiency, and
     that's what actually decided it.
  4. I asked myself whether this ordering decision was "CAP theorem
     consistency" and had to correct my own terminology — CAP theorem is
     about distributed/replicated storage under a network partition, a
     different problem from this single-database, sequential-operations
     ordering concern. The closer fit is causal ordering / write-then-read
     consistency within a sequence, not CAP's C.
  5. I explicitly decided against publisher confirms on the
     `notifySenderDelivered` send, tying that decision back to the
     feature's already-established best-effort nature (see solution point
     4 above) — a deliberate scope boundary, not something I overlooked.
  6. Deliberately deferred, not forgotten:
     - Proper Redis error handling inside notifySenderDelivered.js (a
       thrown/rejected `redis.hGet` currently falls into a broad catch that
       nack-discards without distinguishing transient from permanent,
       unlike the more careful categorization I built for Decision 4).
     - The two React frontend gaps (below) were intentionally sequenced
       AFTER this backend feature, by my own choice — not because I
       consider them lower priority in any absolute sense, just ordering.

================================================================================
STILL OPEN / NOT YET BUILT (as of this document)
================================================================================

- Frontend: my OfflineMessages socket callback (client-side) has no real
  error handling right now — it unconditionally calls `callback(true)` for
  every received offline message regardless of whether the message was
  actually processed or rendered successfully on the client. I flagged this
  myself as needing a fix, deliberately deferred until the backend work
  above (Decision 7 and earlier) was done.

- Frontend: single/double/blue tick UI logic isn't built yet at all — the
  backend now emits a `messagesDelivered` event (Decision 7) but nothing on
  the client listens for it or updates message state/UI based on it.

- Redis error handling inside notifySenderDelivered.js: right now any
  error, including a Redis connection failure, falls into a single catch
  that nack-discards without retry, unlike the careful transient-vs-
  permanent categorization I built for MarkDelivery.js (Decision 4).
  Deliberately deferred, to revisit after the two frontend items above.

- No prefetch value set on MarkDelivery's channel — currently unbounded
  (RabbitMQ/amqplib default). A burst of simultaneous reconnects (say,
  after a server restart) could hand this one consumer a large number of
  unacked messages at once, all potentially retrying MongoDB concurrently
  if an outage coincides with a burst like that. I looked into this at
  length, including catching a real misunderstanding of my own: prefetch(1)
  throttles the WHOLE consumer, not a per-user lock — it doesn't actually
  prevent same-user duplicate-reconnect races the way I first assumed it
  did. Left as an open decision, not yet applied. Unrelated to the offline-
  delivery feature itself — see history point 1 under Decision 7.

- I found a bug in this feature while testing it, near the end of the
  session I was documenting from, and hadn't yet diagnosed or described it
  in enough detail to write it up properly here. I was mid-debugging,
  isolating which stage of the pipeline it's coming from, when I moved to
  closing this document out ahead of switching to a fresh session. THIS IS
  A KNOWN LOOSE END — next time I pick this up, first thing is to nail down
  what that bug actually was and whether I've fixed it, since it affects
  how much I should trust Decision 7 as documented above. Decision 7
  describes the DESIGN I agreed to build, not necessarily a design I've
  confirmed is bug-free in practice yet.
